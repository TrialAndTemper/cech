# cech build

Implemented 2026-10-29; not maintained: the code and its tests are current.

What `cech build` reads, what it writes, and how its flags behave.
The ADRs behind it are ADR 13 item 4, ADR 14 items 3 and 5, ADR 15 items 4 and 5, ADR 17 item 7, ADR 18 and ADR 21 item 2.

## Sources

1. `cech build` works on the marketplace in the current folder, or in the folder that `-C` names.
2. It reads `data/marketplace.toml`, and rejects the file when:
   - it has a key the build does not know;
   - `namespace`, `description` or `owner.name` is missing;
   - the namespace breaks the name rules of ADR 12 item 3, or ends in a version such as `-1-4-0` or `-1-4-0-rc-2`;
   - `team` is not of the form `@org/team`.
3. A file without a `cech` key is CECH's own.
   Its namespace is `cech`, and it has no `categories` and no `terms`.
   A file with a `cech` key is an extension's.
   Its `cech` is `X.Y.Z` or `X.Y.Z-rc.N`: decimal, with no leading zeros, and `N` from 1.
   Its namespace is not `cech` and does not start with `cech-`.
4. Each category an extension adds must have a name that follows ADR 12 item 3, and a `holds`.
   The name must not be one of CECH's, or be added twice.
5. Each role must have a name that follows ADR 12 item 3, and a `means`.
   The name must not start with `cech-` or be defined twice.
   In an extension, it must start with the namespace and a hyphen.
6. Each path in `terms.rules` and `terms.names` must lead from the repository root to a file inside it.
7. CECH's categories, and what each holds, are in `cli/internal/marketplace/categories.toml`.
   The CLI builds this file in and holds it to rule 4.
8. Each folder in `plugins/` is a category, and each folder inside a category is a plugin.
   The build rejects a category or plugin folder whose name breaks ADR 12 item 3.
   It also rejects two plugins with the same name.
   It does not check that a plugin's category exists or that its name has the namespace prefix; `cech validate` does.
9. For each plugin, the build reads three kinds of file:
   - `.claude-plugin/plugin.json`.
     Its `name` must be the folder's name.
     `author.url` is optional, and must be a string.
     `metadata` is optional, and must be an object.
     `metadata.maintainers` is optional, and must be an array of GitHub user names.
   - `skills/<name>/SKILL.md`.
     Its frontmatter must have a `name` equal to the plugin's, and a `description` that is a non-empty string.
     No key may appear twice at the top level.
   - Each `agents/<agent>.md`.
     Its frontmatter must have a `name` and a `description`.
10. The build reads the root `LICENSE`, if there is one.
    It rejects anything at that path that is not a file.
11. When the sources break any rule above, the build writes nothing.
    It names each file or folder it rejects, with the first problem it found there.

## Generated files

12. In each `plugin.json`, the build sets two fields:
    - `description`, copied from `SKILL.md`;
    - `version`, which is `0.0.0-dev`, or `V` in a release build.

    A field it adds goes right after `name`.
    In an extension, each dependency written as an object whose `name` starts with `cech-` also gets a `marketplace`.
    Its value is the name of the CECH release in `cech`, such as `cech-0-1-0` for `0.1.0`.
    Every other byte of the file stays as it was.
13. `.claude-plugin/marketplace.json` has:
    - a `name`: the namespace, or `<namespace>-V` in a release build;
    - the `description` and `owner` from `data/marketplace.toml`;
    - for each plugin, its `name`, `source`, `description` and `category`, sorted by category and then by name.
14. Beside each reviewer agent's Markdown, the build writes a Codex agent, `agents/<agent>.toml`.
    Its first line names the Markdown it came from.
    Then come `name`, `description`, `sandbox_mode = "read-only"`, and `developer_instructions`, which holds the Markdown's text after the frontmatter.
    The build removes any other `.toml` file in `agents/`.
15. Each skill folder gets `skills/<name>/LICENSE`, an exact copy of the root `LICENSE`.
    Without a root `LICENSE`, the build writes no copy, and leaves alone any copy already there.
16. When `data/marketplace.toml` has a `team`, the build writes `.github/CODEOWNERS`:
    - first, a catch-all line, `* <team>`;
    - then, for each plugin, a line for `/<plugin folder>/` that names the owner and the maintainers.

    The owner is `<user>` when `author.url` is `https://github.com/<user>`, unless `<user>` is the team's organisation.
    Each name appears once, whatever its case.
    A plugin with no one to name gets no line.
    Without a `team`, the build removes a code owners file that starts with `# Generated by cech build`, and leaves any other.
17. `docs/catalogue.md` has two kinds of table:
    - one of the categories and what each holds: CECH's first, then any the extension adds;
    - one per category, of its plugins and their descriptions.
18. A generated file whose format allows comments starts with a line saying that `cech build` generated it.
    A licence copy has no such line.
    Every file the build writes from scratch has LF line ends and a final newline; a licence copy is not written from scratch.
    A second build changes nothing.
    A file the build rewrites keeps its mode.

## Modes and output

19. Without `--check` or `--dry-run`, the build writes the generated files.
    For each file it changes, in path order, it prints `created <path>`, `updated <path>` or `removed <path>`.
20. With `--check`, the build writes nothing.
    For each file that differs from what it would write, it prints `create <path>`, `update <path>` or `remove <path>`.
    It fails when any file differs, and says on stderr how many do.
21. With `--dry-run`, the build prints the same lines as `--check`, but does not fail.
22. With `--json`, the build prints one object with `mode`, `ok`, `files`, `skipped` and `errors`.
    Each entry in `files` and `skipped` has a `path` and a `change`.
23. `--release V` takes `V` as `X.Y.Z` or `X.Y.Z-rc.N`, in the same form as the `cech` key.
    Any other `V` is a wrong command line.
    When an extension's `cech` is a pre-release, a release build of a final `V` fails and writes nothing.
24. The exit status is:
    - 0 when the build is done;
    - 1 when it cannot build from the sources, when files differ under `--check`, or when a write fails;
    - 2 for a wrong command line;
    - 3 when it cannot open the root or is denied a read, and nothing else failed.
25. When a write fails, the build reports the files it changed.
    It also reports, on stderr and in `skipped`, the files it did not change.

## Gate

26. `mise run build:check` is part of `mise run check`.
    It builds `cech` from the checkout and runs `cech build --check` on the repository.
    `mise run build:fix` runs `cech build` with the same `cech`.

## Notes

- Checked on 2026-10-28 with Claude Code 2.1.312: `claude plugin validate --strict` fails on a catalogue with no `description`, and accepts one at the top level.
  So the catalogue carries the description from `data/marketplace.toml`.
- A licence copy has no generated-file line, so the build cannot tell an old copy from a file written by hand (rule 15).
